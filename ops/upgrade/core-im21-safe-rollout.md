# CORE im.21：停流、一次迁移、整组放行

**这不是线上部署脚本。** 只适用于已审查的 im.21 修复构建、Linux Docker Engine、PostgreSQL 主库和日志库（允许同库）及 Redis。以下需要在隔离副本演练；真实维护窗口、数据库写入、镜像发布和切流另行授权。不要用 im.13/im.18 的切换或回退脚本。通用的 `docker compose up -d` 不是这个版本的发布程序。

### 准备并锁定变更范围

- 从独立的发布记录核对**通过验收的完整 Git SHA、签名镜像的规范 repository@sha256 摘要、目标架构**，而不是上线后向某个容器询问“你是哪个版本”。固定 `NEW_API_IMAGE`。OCI 修订标签需等于完整 SHA，版本标签需为 `v1.0.0-rc.51.chuanapi.im.21+g<前12位SHA>`；裸版本、同名 tag 都不够。启动时校验的迁移收据还绑定**实际二进制**，所以使用相同平台的同一构建；不能把不同架构的二进制视为同一迁移。
- 在独立的控制面核对 **所有**负载均衡后端（所有入口、私网直连、曾用节点、预备/蓝绿/灾备）、所有 master/定时器/队列消费者和可重建它们的编排控制器。不要拿当前负载均衡的几条健康记录代替全量清单。非 Docker 节点或无法盘清的主机：**不放行**。禁止把业务容器列为基础设施。基础设施只免于候选镜像匹配，不免于按名字和既有不可变容器 ID 核实。
- 专用发布机保存受保护的 inventory 文件。每个受控 Engine 都给出已从资产清单核对的 ID 与一个本机 Unix socket；远端可通过此前核实主机密钥的 SSH Unix-socket 转发。文件、socket、转发端点与宿主机仅可信发布账号能控制；不接收浏览器、工单、业务 API 提交的路径或 JSON。不暴露 Docker TCP 接口；普通 Docker socket 具有宿主机级权限，优先提供只允许本工具所需 GET 的本机代理。
- 登记无凭据的 `stores`（小写 DNS 名、显式端口和数据库名/Redis 索引；同库时 `log` 填与 `primary` 相同）。每个容器实际配置中的地址均需匹配，数据库用户和密码不必相同。此门禁仅支持简单的 PostgreSQL/Redis TCP URL，PG 可带单个 `sslmode`；其他查询覆盖、服务别名解析器、IPv6 URL 等未审核形式拒绝，不要因此放松生产 TLS 或数据库权限。跨主机必须另行核对 DNS/路由指向同一真实服务，特别是 Redis；相同字符串并非同一集群的证明。
- 用密码学随机源生成新的非秘密 32 位小写十六进制 `CORE_IM21_RELEASE_ID`（如 `python3 -c 'import secrets; print(secrets.token_hex(16))'`）；不得复用到另一窗口、克隆库或环境。写入本次 plan 并提供给迁移容器及每个服务进程。主/日志收据由程序在实际数据库写入并验证，绑定此窗口、同次迁移及实际二进制。PG DDL 凭据仅给迁移作业；服务进程只给运行所需权限，不给修改迁移收据/DDL 的权限。不得把 DSN、密码、镜像认证信息写进发布记录。
- 单独核对基线备份及其**在隔离机上**的恢复结果，留存收据、审核人、发布镜像和活动配置；明确值班人员、最长停流时长和中止条件。对 PG 主/日志、Redis、钱包/订单、报价、授权、审计建立一致性检查。备份不是无损原地回滚。

**计划文件示意。** 尖括号必须替换。第二个主机只是拓扑示例，不表示线上有两台；同一 master 同时处理 HTTP 和后台任务时仅列一次。所有主机都要列，它们的**全部容器**（含停止的）都必须在对应阶段有明确归属。对不适合封闭清单的共享或动态集群，不提供放行。

~~~json
{
  "revision": "<完整40位SHA>",
  "image": "registry.example/team/new-api@sha256:<64位摘要>",
  "release_id": "<本次窗口新生成的32位小写十六进制>",
  "opens": "<UTC开始时间，例 2026-11-23T10:00:00Z>",
  "expires": "<不超过24小时的UTC结束时间>",
  "personal_pricing": true,
  "stores": {
    "primary": "postgresql://pg.example:5432/main",
    "log": "postgresql://pg.example:5432/log",
    "redis": "redis://redis.example:6379/0"
  },
  "hosts": [
    {"socket": "/run/core-engine-a.sock", "id": "<已核对的Engine-A-ID>",
     "nodes": {"new-api": "master"}, "migrator": "core-im21-migrator",
     "infrastructure": {"postgres": "<该现有容器64位ID>", "redis": "<该现有容器64位ID>"}},
    {"socket": "/run/core-engine-b.sock", "id": "<已核对的Engine-B-ID>",
     "nodes": {"new-api": "slave"}, "migrator": null, "infrastructure": {}}
  ]
}
~~~

### 放行步骤（顺序不可跳）

先在边缘/LB、内网、控制面及任务入口建立**外部维护屏障**，包括普通流量、后台写操作、自动任务、供应商提交、价格/授权/目录保存以及通用 option 写入。不要仅隐藏按钮或仅匹配特定 POST 路径；旧程序不理解新的环境开关。暂停自动伸缩、自动回退和自动重建旧镜像，完成长连接、在途账务与队列排空；不要丢弃或重复结算。保留这一屏障和发布互斥锁直到最后一关结束。

在受保护的终端运行一次完整的门禁：

~~~sh
python3 ops/upgrade/core_im21_guard.py window --plan /protected/im21-window.json
~~~

门禁在每一步等候。由已获授权的运营人员在另一终端完成该步并按 Enter；Enter 不代表“通过”，只是发起实际检查。仅允许此 **window 进程最终返回 0** 后继续人工复核/切流；不要把该命令的输出导出为长期有效的授权。任一非零、退出、超时、会话丢失均保持屏障；单独运行 `drained/migrated/locked/active --plan ...` 只能排查，不能接续或代替完整流程。

1. **drained**：下线、排空并移除旧服务和工作容器（不删持久化卷），不启动候选。确认 LB/所有直连、主机进程管理、队列、PG 活动连接里没有遗漏的业务实例。只保留预先登记的基础设施。门禁全量枚举各 Docker Engine（包括已停止容器）；任何遗留、少列一个或某台不可达都阻止迁移。
2. **migrated**：只启动一个作业，禁止发布端口、自动重启或进负载均衡；`CORE_IM21_MIGRATION_MODE=migrate`，`NODE_TYPE=master`，`CORE_IM21_ROLLOUT_MODE=locked`，`USER_GROUP_PRICING_ENABLED=false`，同一已批准镜像和窗口 ID。仓库提供专用 Compose profile：
   ~~~sh
   docker compose --profile core-im21-migration run --no-deps --name core-im21-migrator new-api-migrate
   ~~~
   **不要加 `--rm`、`--service-ports`、`--entrypoint`、`--version`，不要把 `up` 的返回视为迁移成功。** 先等真实作业已退出且退出码为 0；保留已退出容器作为此后各关的证据。门禁检查 job 的实际镜像、入口参数和运行状态。迁移锁忙、预检不通过、主/日志库部分失败或超时，一律不启动服务，不取消检查。先排查冲突和数据问题；重复演练使用受控的新窗口，不要伪造收据。
3. **locked**：流量和写入源仍全部隔离。仅启动经审查的候选服务容器，`CORE_IM21_MIGRATION_MODE=serve`、`CORE_IM21_ROLLOUT_MODE=locked`、个人定价关闭，同一 `CORE_IM21_RELEASE_ID`。所有 master（含后台角色）和 slave 必须在迁移结束之后启动并通过各自私有 `/api/readyz`。每个服务容器的有效 `NODE_NAME` 必须显式且全局唯一，避免多个实例覆盖彼此心跳或审计归属；多主机不要全部沿用 Compose 的默认节点名。核对主/日志库收据、应用监控、队列、授权、报价/账务基线和 readiness；未就绪不补跑服务端 DDL。门禁同时核实容器实际内容镜像 ID、该镜像的 RepoDigest、完整修订标签、未替换入口、角色及发布配置；跨两次枚举发生变化即拒绝。
4. **active**：第三关全部通过后才允许把所有候选服务重建为 `CORE_IM21_ROLLOUT_MODE=active`。`USER_GROUP_PRICING_ENABLED` 在所有节点统一为 plan 约定值（要启用填写 `true`，否则 `false`）。不可对新旧池做百分比分流；新旧计价也不可同时服务在途流量。屏障和任务源隔离仍有效；保持外部触发、后台自动化和新功能写入口封锁，**直到最后一个候选也以相同政策通过检查**。迁移作业不重跑，收据不替换。
5. **开放**：窗口进程返回 0 后，运营人员在同一控制面锁内重新核实 LB 实际后端、遗漏节点、数据源、队列与监控。一次性切换到**已验明的这一组**，然后才恢复用户、管理员和任务入口。管理写入、专属组越权/允许样例、个人倍率实际扣费、旧 Key 路由、新联系方式/平台值的写入再编辑与审计，都先用已授权的受控账号验证。若拓扑、镜像、配置或部署代次改变，之前的点时检查失效。只有门禁副本检查通过不能代替外部屏障。

### 故障与回退

**默认拒绝**：`python3 ops/upgrade/core_im21_guard.py rollback` 总是返回非零。没有已获批准的兼容回退镜像，本流程因此不允许任何原地降级，包括裸 `0dff956284eda773db217445724d1d85e8d0b840`，不论 flag、表数或当前抽样显示什么。还必须保留所有未完成或待结算异步任务的费率快照（包括非个人定价）；旧 worker 可能忽视接单时的计费快照，不允许把队列交给旧 worker。旧程序即使能启动/显示旧 UI，也可能错误放行专属组、忽略个人倍率、或不能重提 Telegram 及新平台报价。仅删除授权、清空报价、切换旗标或还原旧库会丢失语义/数据，不是回滚。也不要在已有专属授权/有效个人定价的实例上倒切到 locked 或关闭计价后放行。

**恢复策略**：保持维护/隔离，保留两库与 Redis 的当前持久状态、备份和证据；不自动重试结算。仅 UI 有问题时优先继续运行同一个已验证后端；旧 UI 如需使用，先针对该后端和当前真实表示进行隔离验证（缓存、读写、未知枚举、新权限、报价编辑）后另行审批，本分支不提供已验证的旧前端。单实例失败优先用已经通过放行的**相同**镜像、窗口、主日志库、角色和有效计价配置恢复该实例；在私有 readiness 和业务校验通过前不接流量。需要修改程序或原地降级时保持屏障：在受控副本保留新写入，制作前向修复或专用兼容回退，重新审查并单独批准迁移/恢复程序。已有新状态被 locked 检查拒绝不是清空数据的理由；本“首次激活”流程不能用于绕过该拒绝。

未来若要支持兼容回退，至少用真实目标构建在隔离 PG 副本实测“升级 → 新授权/新个人价格/新报价落库 → 不恢复旧库切到兼容版 → 读写/计价/授权仍正确 → 回到新版”，同时核对两库模式、白名单、任务/订单、Redis 和审计，必要时仅更换演示层。对 live 状态的未知或非法 JSON 不是“未使用新功能”。检查脚本本身只用 Engine GET，不做数据库查询、镜像拉取、容器执行或任何切流；它不能约束拥有宿主机权限的人工旁路、漏报的宿主机或控制面的后续漂移。未满足这些前提就保留维护状态。
