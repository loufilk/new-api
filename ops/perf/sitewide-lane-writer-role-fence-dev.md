# PostgreSQL old-writer fence, isolated rehearsal

This is an explicit PostgreSQL 18.6 rehearsal, not an installer for an existing database. The runner always creates a new loopback cluster, a random fixture marker and a dedicated database. No production bootstrap, endpoint, automatic migration, wallet grant or live provider exists. Ordinary and managed startup remain disabled for custody.

The legacy SCRAM login initially holds one live uncommitted update and a separate prepared update. Commit NOLOGIN plus database CONNECT removal first. An old physical session can still see its uncommitted value after that change. Terminate only its exact synthetic PID, backend start time and authenticated role on the fixture database, with a positive wait, then verify that it cannot commit and the original value is intact. The prepared transaction is still present after both old sockets exit and prevents a seal until explicitly resolved. The seal records configured 2PC capacity and zero unresolved 2PC in the sole writable fixture database.

The verifier requires separate non-owner old/next/probe roles, a NOLOGIN protected database/schema/table owner, no role membership or elevation paths for these roles, exact SCRAM-only loopback HBA with no Unix socket, closed PUBLIC database admission, no additional CONNECT-capable login, and a quiet database including background sessions. It rejects unlisted objects, routines, listeners covered by database sessions, triggers, rewrite rules, subscription state, and unwanted effective table/column ACLs. Old credentials cannot reconnect or authenticate as the next role. Only the separate current login can update the bounded synthetic units column; it cannot alter the ID, catalogue or protected receipt. These are synthetic limits, not the production writer roster.

The evidence row is protected by the separate database owner and revalidated through a fresh auditor connection, with cluster, database/schema, role and relation identities and exact prepared release/epoch receipts. Unlogged evidence is rejected, and a later privilege, relation constraint or epoch change invalidates current approval. Do not treat the row, a process snapshot or NOLOGIN alone as an operational grant. A DBA, OS/HBA changes, an unlisted service/worker or direct client, or an old process obtaining the new credential, are outside this rehearsal. Production requires inventoried writers and every writable endpoint; independently provisioned new credentials, revoked old admission and privileges, pool/worker quiescence, explicit unknown/prepared-transaction resolution, protected writer/DDL roles, and continuously enforced handover/rollback. Restore or server failover must be independently re-proved; this only tested a fresh connection on the same endpoint.

PostgreSQL 18 references: [role membership](https://www.postgresql.org/docs/18/role-membership.html), [backend signaling](https://www.postgresql.org/docs/18/functions-admin.html), [monitoring](https://www.postgresql.org/docs/18/monitoring-stats.html), and [prepared transactions](https://www.postgresql.org/docs/18/view-pg-prepared-xacts.html).
